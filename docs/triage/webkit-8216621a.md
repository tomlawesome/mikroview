## 2. live-topography-tunnels.mjs -- fit chip does not restore the frame

Gate failure: two checks in one run -- `FAIL the fit chip returns to the
fitted frame (1.6 0.8 1400 720)` (restore after a hand pan) and `FAIL and
the fit chip brings the whole map back again (got 351.5 180.5 697 358.5,
want 0 0 1400 720)` (restore after a wheel zoom). Second WebKit sighting
of this scenario; first sighting is closed issue #1323 and
`docs/flakes.md`'s existing entry.

WebKit, alone, 3 runs:

| run | load avg | result |
|---|---|---|
| 1 | 4.05 4.46 4.74 | PASS (`got 0 0 1400 720, want 0 0 1400 720` on both restores) |
| 2 | 4.19 4.45 4.72 | FAIL -- `the fit chip returns to the fitted frame (138.2 69.1 1400 720)` (pan restore); the wheel-zoom restore passed |
| 3 | 3.12 4.16 4.62 | PASS (same clean values as run 1) |

Chromium, alone, 2 runs -- both PASS, both restores clean.

**Class: flake, but reproduces alone under WebKit (~1/3 of runs here) --
not host contention.** #1323 asked, in order, whether this is a real
restore fault or a string-formatting artefact. Both the gate run and my
run 2 answer that: the numbers are genuinely different each time (e.g.
`138.2 69.1` vs `0 0`), and which of the two restore checks fails varies
between runs -- a real, WebKit-specific timing race in the fit-restore
path, not a rounding or serialisation issue. This is the third distinct
WebKit sighting of the underlying fault (2026-09-22 first sighting,
this gate run second, my repro run third) -- past the point
`docs/flakes.md`'s own rule would file an issue. Per this task's scope
(no issue edits), that step is left to the owner; recorded as sightings 2
and 3 under the existing flakes.md heading. No file:line cause identified
-- pinning the exact race needs instrumenting the fit/zoom restore code,
out of scope for this investigation-only pass.
