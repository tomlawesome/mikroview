# Pre-release review: v0.5.1

Reviewed: `8fd5c5ab` (dev after the router-backup custody merge, !1026;
first pass) and `ed2f97a4` (the `fix/router-backup-custody-review` batch
carrying every first-pass fix; second pass and security). The release
changes nothing else after `d7b820b4`, the v0.5.0 audit head, other than
the flake record and the RouterOS push-script fix (#955), which the first
pass covered. The next release reviews what changed after `ed2f97a4`.

**Disclosure rule.** As for v0.5.0: security findings appear here only
once fixed, merged to `main` and named with their fix commit; anything
open lives in a confidential issue. This file is never deleted.

## Method

Four finder agents per pass, one per dimension -- quality, efficiency,
robustness, professionalism -- each briefed to read the diff and the code
around it, judge only its dimension, and give every finding a concrete
failing scenario. The primary agent then made the security pass on the
final head, reading the routes and the vault code end to end rather than
the diff. Every finding was fixed on the same batch, most with a test
that failed on the unfixed code; the exceptions say so below. Finders:
Claude Sonnet 5; fixes: Claude Sonnet 5 and Claude Fable 5; triage,
design rulings and security: Claude Fable 5. Owner ruling 2026-09-11: every
finding gates the cut, none deferred.

The gating findings: a backup arriving during a passphrase removal was
sealed to a key that was then deleted (permanent loss); two passphrase
changes could interleave; the per-token ingest limit made any backup over
about 3.8MB undeliverable; vault errors carrying server paths reached the
router as a 400; the private key stayed in memory in cases the feature
promised it was dropped; a failed vault write left a phantom generation.
Issue bodies hold the detail; #1112 holds the triage note.

Design ruling on #1125 (owner, 2026-09-11): the vault never refuses a
backup for want of space. Low on disk it keeps, per router, the newest
generation from before the trouble (the anchor) and the newest arrival,
and cycles the generations between them. Admin-protected backups with
their own pool are #1126, after this release.

## Security

Made by the primary agent on `ed2f97a4`, reading `internal/api/{routerbackups,routerbackupslock,ingestbackup,auth}.go`,
`internal/backupvault/{vault,lock}.go` and `internal/backupslice/slice.go`
in full, plus `main.go` wiring. Checked: all four lock routes are
admin-gated (test covers the DELETE); a slice for another device's
transfer is indistinguishable from an unknown transfer; ingest bodies are
capped at 64KiB with unknown fields refused; unlock attempts are
throttled and `unlock_failed` is audited only on a wrong passphrase, so a
throttled caller cannot fill the audit log; `SetPassphrase` stops sealing
under the retention key before the reseal, so nothing lands unlockable;
`RemovePassphrase` seals arrivals under the retention key for the whole
pass; the start-up reconcile deletes files only when the index loaded
cleanly, so a missing or corrupt index deletes nothing; no vault error
text reaches a router -- sink failures answer 503 with a fixed message and
audit as a server fault.

The two confidential findings from pass 1 (#1120 key residue, #1122 error
echo and audit) are fixed on this batch -- 846810ab, 718eae4c, 3e888df5,
f60fb3af, c758a2cd, d0fa13d0, ed2f97a4 -- and will be listed with detail
here once on `main`. No new security finding on the final head.
