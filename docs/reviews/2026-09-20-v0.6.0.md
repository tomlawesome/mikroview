## Method

Six stages in order -- Function, Efficiency, Professionalism,
Robustness, Quality, Safety -- run as sequential passes over the same
head. Each stage is sliced six ways (backend API/auth; backend engine;
the rest of `internal/`; frontend components; frontend lib and scripts;
ops) plus a property pass that reads one property across the whole tree
rather than one directory (every store against logout, every value
reaching a pasted command, every route against the authorization
matrix). One finder per slice per stage, judging that lens only. Every
medium or high finding goes to an independent refuter, given the
finding and the code but never the finder's reasoning, and briefed to
refute on uncertainty. The primary agent judges what survives.

Security runs once, alone, last, after every stage is fixed, on the
final head, under four lenses: role and auth gates against the
authorization matrix; every secret from mint to storage, log and
display; every value reaching a pasted RouterOS command; and account
state left behind after sign-out.

Every fix carries a test that fails before it and passes after, and
gets its own fix review. Each fix batch is re-audited by a session that
did not write it -- the session that writes a batch of fixes cannot
also be the one that checks them.

Finders and refuters: Claude Sonnet 5. Judging: Claude Opus 5 for the
first pass, Claude Fable 5 for the fix batches and the final pass. Design
rulings: the owner, on Claude Fable 5 proposals. Tracking issue #1257.

## Security

Runs once, alone, on the final head (`9cb25401`, the range
`0f3684e5..9cb25401`, 116 commits, 149 files), after every stage above
was fixed. Eight finders sliced by directory (api, data, command text,
components, lib, ops, docs) plus a property pass, under the four lenses
in the Method section above. Every finding went to an independent
refuter.
The six commits that followed on the branch (the three owner-ruled
fixes, one test follow-up, one static-analysis annotation) each had a
fix review under the same lenses rather than a fresh stage.

One finding, on the final head:

| Sev | Where | Finding | Fix |
|---|---|---|---|
| low | `.dockerignore`, `Dockerfile` | A recorded upgrade fixture directory (password and token hashes, a TLS key, used only for local testing) was gitignored but not dockerignored, so `docker build` could send it into the build context and the layer cache on a developer machine that had fetched one locally | fixed `dfeb3967`: `.dockerignore` entry plus a test that fails against a populated fixture directory |

Refuted narrower: no CI job that builds the image also fetches a
fixture, and the final image copies three explicit paths, never the
build context -- so the only real exposure was `make container` on a
developer machine after a local fetch.

Earlier in the cycle, before this final head, two more security-grade
findings were fixed on the batch:

| Sev | Issue | Finding | Fix |
|---|---|---|---|
| high | #1281 | A device with syslog access could claim another router's address, and an admin session alone could open the syslog port to an unenrolled sender -- attribution rested on which address a request claimed, not on proof of who held it | `52a47050`, `4cea14f0`: an address is accepted as a log source only once a one-time, single-use token, minted after the admin re-enters their password, arrives in syslog traffic from that address. Registering a router in the wizard grants nothing. |
| high | #1294 | Deleting an unreadable vault index to get the service running, then restarting normally, later deleted every backup the rebuilt index did not name -- kept generations and the retention anchor included. Repair also deleted the intact half of a damaged generation, kept ones included | `97ef5d14`: a missing or unreadable index is rebuilt from the files found on disk and every recovered generation is kept; repair demotes a damaged generation instead of deleting its surviving half, and drops it only once both files are gone |

Nothing exploitable was found, on the final head or across the batch.
